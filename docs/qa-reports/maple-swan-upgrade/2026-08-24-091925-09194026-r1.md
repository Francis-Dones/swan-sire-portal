## Findings

- 🟥 Critical — `app/Http/Controllers/ExamController.php:31-78` — `index()` now paginates
  server-side (`getExams(['per_page'=>20,'page'=>$currentPage])`, matching swan-api's new
  paginated `{success,data,meta}` shape) but still applies `search`/`vessel_name`/`date_from`/
  `date_to`/`review_status` filtering **client-side on only that one 20-item page**, then builds
  the `LengthAwarePaginator` with `$meta['total']` — the *unfiltered, all-pages* total from the
  API. Confirmed the API's `GET /exams` (`TbExamController::paginated`) has no server-side
  search/filter support at all, so this is the only filtering that happens.
  ```php
  $result = $this->api->getExams(['per_page' => $perPage, 'page' => $currentPage]);
  $allExams = $result['data']['data'] ?? $result['data'] ?? [];   // 20 rows, one page
  ...
  if ($search) { $examsCollection = $examsCollection->filter(...); }   // filters only those 20
  $paginatedExams = new LengthAwarePaginator($examsCollection->values(), $meta['total'] ?? ..., ...);
  ```
  Effect: any search/vessel/date/review_status filter silently misses every match outside the
  currently-viewed page — a reviewer searching for an exam_id, or filtering to `pending`, gets
  wrong (incomplete or empty) results with no error, while the pagination footer still claims
  the unfiltered total. The "vessel dropdown options are always derived from the full set" code
  comment at line 40 is now false — `$vessels` is derived from the same 20-item page. The
  `else` branch ("Backward compatible fallback... API may still return the old, unpaginated
  shape") is dead code: swan-api's `paginated()` helper always includes `meta` now, so that
  branch never executes. This directly undermines plan item 4 (review-status filtering /
  batch-grouped review) for any vessel/fleet with more than one page (20) of exam history.
  Fix direction: either have the portal fetch the full result set for filtering (as the old code
  did, and as `InspectionImageController::vesselOptions()` still does via `per_page=500`) and
  paginate/group client-side over the complete set, or push `search`/`vessel_name`/`date_from`/
  `date_to`/`review_status` down as real query parameters to a swan-api endpoint that supports
  them. (confidence: high)

- 🟨 Improvement — `app/Services/ApiService.php:150-154` (pre-existing, not touched by this
  diff — the line above the diff hunk was already there at checkpoint 67df71e) —
  `Log::info('External API login response', [..., 'body' => $response->json()])` logs the full
  login response, including the plaintext bearer token, to `storage/logs/laravel.log`. Out of
  scope for this review (unchanged by the diff) but worth a separate ticket since it sits right
  next to code this PR did touch (`device_name` was added two lines above it).
  (confidence: high, pre-existing — does not block this review)
